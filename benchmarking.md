# Benchmarking Guide

How to set up and run reproducible benchmark evaluations.

## Current strict-superiority status

Corpus-wide strict superiority over TLC in both runtime and memory is **not
established**. The current result is unknown after the July 21–23 engine
changes. The definition of done, current evidence, and ordered blockers are
tracked in the internal TY-vs-TLC strict-superiority burndown, which is not
part of this snapshot; the remaining measurement blockers are summarized
below.

The broad matrix refresh currently collects runtime evidence, not a complete
both-axis scorecard. Targeted `supremacy compare` now provides repeated paired
runs and can collect peak RSS, but complete-process-tree memory is still a
separate blocker. Its performance defaults require TLC/TY runtime speedup
`> 1.05` and TY/TLC peak-RSS ratio `< 0.95`. Protected launch and enforced
matrix collection pin native compilation to one job, but neither tool is yet
confined with OS-level CPU affinity. These remaining gaps are measurement
blockers, not proof of a current loss or win.

## Quick Start

```bash
# Build the release Rust CLI binary used for benchmark evidence.
CARGO_TARGET_DIR=target/user CARGO_NET_GIT_FETCH_WITH_CLI=true \
  cargo build \
    --profile release \
    -p tla-cli \
    --bins
TY=target/user/release/ty

# Run the full batchable all-runnable runtime refresh/audit from the binary.
OUT=reports/perf/$(date -u +%Y%m%dT%H%M%SZ)-supremacy-matrix-runtime-full
"$TY" supremacy matrix-full-suite \
  --baseline tests/tlc_comparison/spec_baseline.json \
  --mode warn \
  --format json \
  --runtime-output-dir "$OUT" \
  --runtime-ty-bin "$TY"
```

## Launch-gate governance (the Rust CLI is the sole gate)

The `ty` Rust CLI is the authoritative entrypoint and the documented launch path
for trust-codegen single-thread evidence and launch gates. Concretely, **only
`ty supremacy gate --mode enforce --gate-mode full-native-fused` is the final
single-thread launch gate** — `matrix` / `matrix-full-suite` produce broad
all-runnable refresh and audit evidence, but **a matrix summary cannot replace the
final three-spec single-thread launch command**, and **this document does not claim
that all-runnable matrix enforcement currently passes**.

Final benchmark collection and policy verdict must run through the Rust CLI. The
**Python/JQ all-runnable classifiers, spec allowlist gates, ad hoc benchmark-verdict
scripts, and Python TLC-vs-TY perf gates have been removed as gates**. **Retired
Python benchmark and fast-subset helper paths have been deleted and must not be
recreated, sourced, or treated as launch evidence.** **Historical reports and
superseded designs may still quote those deleted command paths as archived
provenance, not runnable guidance.** Likewise, **generated bytecode caches or
archived report text are not executable gate surfaces.**

Current deletion audit: no Python or JQ source path is accepted as a canary,
supremacy, or launch gate. The thin shell wrappers under `scripts/` remain only as
delegating compatibility surfaces that preserve the Rust CLI's exit code — **the
remaining blockers to deleting the shell compatibility wrappers are operational
callers**, not gate logic.

## trust-cg Single-Thread TLC Evidence

Use the `ty` Rust CLI as the authoritative entrypoint and documented launch
path for trust-cg single-thread evidence and launch gates. There are two Rust gate
families:

- `ty supremacy ...` owns single-thread TLC/trust-cg launch evidence.
- `ty canary-gate ...` owns launch-adjacent product canaries, including the
  silent eval-error coercion scanner.

For supremacy evidence:

- `ty supremacy smoke` runs the bounded native-fused smoke readiness checks.
- `ty supremacy benchmark` runs the benchmark corpus through TLC, the TY
  interpreter backend, and the trust-cg backend, then writes `summary.json`,
  `summary.md`, and per-run command/stdout/stderr artifacts.
- `ty supremacy compare` is the Rust TLC-vs-TY parity/speed/peak-memory gate for
  targeted baseline or explicit spec comparisons. It replaces Python perf-gate
  scripts for comparison evidence and writes `compare.json` and `compare.md`.
  Enforced performance comparisons use an even count of at least six paired
  repetitions; this remains targeted rather than broad or final launch
  evidence.
- `ty supremacy gate --summary-json <summary.json>` evaluates an existing
  benchmark summary or `ty.supremacy.matrix_summary.v1` artifact with the
  Rust policy-verdict engine and writes `policy_verdict.json` plus
  `policy_verdict.md`.
- `ty supremacy gate` without `--summary-json` first runs the Rust benchmark
  path, then feeds the produced `summary.json` into the Rust verdict engine.
- `ty supremacy matrix` classifies every row in
  `tests/tlc_comparison/spec_baseline.json` against candidate all-runnable speed
  requirements. It is runtime matrix evidence only; it does not establish an
  all-test or total runtime-and-memory supremacy result.
- `ty supremacy matrix-full-suite` is the Rust convenience entrypoint for the
  full batchable all-runnable matrix refresh/audit. It is broader corpus
  runtime evidence than the launch-corpus gate, but it is not launch acceptance
  or a both-axis result.

The executable Rust evidence commands are the Rust CLI commands above, but only
`ty supremacy gate --mode enforce --gate-mode full-native-fused` is the final
single-thread launch gate. The release command should include repeated runs,
currently `--runs 3`, for the three-spec single-thread launch corpus. Python
benchmark, profile, diagnose-selection, or ad hoc JSON-filter helper scripts may
still be useful for local investigation, and legacy script paths may exist to
preserve automation compatibility, but they are not acceptance gates for
single-thread supremacy evidence. Do not close or audit #4392-style
single-thread launch work from Python/JQ allowlists, wrapper summaries, or
hand-picked spec lists. Use `ty supremacy compare`, `ty supremacy matrix`,
`ty supremacy matrix-full-suite`, and `ty canary-gate` only for their
corresponding targeted comparison, matrix, all-runnable refresh/audit, and
product-canary claims.

Fairness controls for TLC-vs-TY timing evidence:

- Rust supremacy commands scrub ambient `JAVA_TOOL_OPTIONS`,
  `JDK_JAVA_OPTIONS`, `_JAVA_OPTIONS`, and `TY_*` settings before subprocess
  launch unless the command explicitly records the override in `command.json`.
- Java TLC runs use recorded single-thread JVM controls:
  `-XX:ActiveProcessorCount=1`, `-XX:+UseSerialGC`, `-Xms64m`, and `-Xmx4g`,
  plus TLC `-workers 1` for launch benchmarking.
- `ty supremacy compare --mode enforce --policy parity-and-speed` and
  `--policy parity-and-speed-and-memory` reject
  opaque `--tlc-bin`/`TLC_BIN` wrappers because their JVM heap, GC, and thread
  controls cannot be audited from the Rust artifacts. Use the Java TLC jar path
  for enforced speed evidence; wrapper-based TLC runs remain diagnostics.
- Enforced speed evidence is single-thread evidence: `compare` requires
  `--workers 1`, an even `--runs >= 6`, and rejects TY-only `--ty-flag` values.
  Odd pairs launch TLC then TY; even pairs launch TY then TLC, giving both
  orders equal representation, with each pair in a distinct `run-NNN` artifact
  directory. The v2 report keeps every raw
  observation and launch order. Performance is gated on the median of the
  within-pair TLC/TY runtime ratios and TY/TLC peak-RSS ratios, never a ratio of
  independently aggregated samples. Missing metrics or TY engine provenance,
  any pair-level parity failure, or cross-pair verdict/count/engine-tier drift
  fail closed. The final launch gate rejects ad hoc `--ty-flag`, `--interp-env`,
  and non-policy `--trust_cg-env` overrides during collection.

The remaining launch-adjacent product guard for silent eval-error coercion is
also owned by the Rust CLI: run `ty canary-gate --kind silent-error --mode
enforce`. `scripts/check_silent_error_coercion.sh` is a compatibility delegator
only; it must not grow independent scan policy, regexes, corpus selection, or
verdict logic.

```bash

python3 scripts/shared_engine_cold_start_report.py \
  --supremacy-summary reports/perf/<supremacy-run>/summary.json \
  --include-generated-mcc-smoke \
  --matrix-runtime-evidence reports/perf/<matrix-run>/runtime_evidence.json \
  --output "$OUT/shared-engine-cold-start-audit.md"

SHARED_ENGINE_RELEASE_LEVEL_ARGS=(
  --require-component-level "shared_preparation=level_4"
  --require-component-level "trust_ir_trust_cg_compile=level_4"
  --require-component-level "runtime_storage=level_4"
  --require-component-level "fingerprint_admission=level_4"
  --require-component-level "analytical_ay_proof=level_4"
  --require-component-level "replay_proof_validation=level_4"
  --require-component-level "portfolio_winner=level_4"
)
python3 scripts/shared_engine_integration_audit.py \
  "$OUT/shared-engine-cold-start-audit.md" \
  --fail-on-incomplete \
  "${SHARED_ENGINE_RELEASE_LEVEL_ARGS[@]}" \
  --output "$OUT/shared-engine-release-gate.md"
```

This report command does not run a benchmark and is not an acceptance gate. It
breaks existing artifacts into shared-engine stage buckets: frontend import,
prepared-program build, trust-ir/trust-cg compile, native execution, ay/analytical
solve, and replay/validation. Stages without first-class timing are reported as
residual or presence-only evidence so architecture work does not overfit to a
named TLA+ benchmark or mistake a native-execution win for a cold-start win.
The follow-on integration audit is the release-critical shared-engine gate: it
must pass the repeated `--require-component-level` arguments above so missing
component rows, omitted `architecture_level` claims, and claims below Level 4
fail closed in the release path.

All performance evidence is for one shared high-performance engine with thin
frontend adapters. A speedup discovered through TLA+/Quint, MCC/Petri,
AIGER/BTOR2/VMT, AY analytical lanes, witness/replay, or a future importer is
accepted as performance architecture only when the reusable work lands in
shared core, trust-ir, trust-cg, AY/proof, runtime storage, fingerprint policy,
replay/validation, or portfolio policy and lists the compatible frontend
families that inherit the win or the blocker that prevents default adoption.

Shared-engine evidence must use the canonical frontend-family vocabulary:
`tla_plus`, `quint`, `mcc_petri`, `aiger`, `btor2`,
`vmt_transition_system`, `ay_analytical`, `witness_replay`, and
`future_importer`. The first eight families are concrete current consumers or
compatible targets. `future_importer` is reserved for future adapters and should
appear as a named blocker, for example
`future_importer:awaiting_registered_importer_frontend`, until that importer
registers a canonical payload-to-engine mapping. Do not use benchmark names,
module names, or one-off adapter labels as frontend-family codes.

Fingerprint and storage wins are accepted as shared-engine evidence only when
they are expressed as canonical contracts. A row may preserve frontend-local
source labels such as TLA+ or Quint, but the reusable part must identify the
shared component, canonical fingerprint policy/identity, storage policy
identity, compatible frontend families, blocker status, validation status, and
a concrete second beneficiary that is not the origin family. Treat TLA state
slots, Petri marking vectors, hardware/register vectors, AY solver objects, and
replay/witness steps as different payload layouts over common engine value
kinds. A storage optimization tied only to `tla_state_slots`, a spec name, or an
trust-cg-only flag is diagnostic evidence, not a cross-frontend storage contract.

A passing three-spec `full-native-fused` gate is launch evidence for the current
native-fused hot path. It is not a total or all-test supremacy claim, and this
document does not claim that all-runnable matrix enforcement currently passes.
A future broad strict claim is tracked by the internal strict-superiority
burndown (not part of this snapshot),
not by the runtime-only matrix alone. Every eligible row must have verified
TLC/TY parity, equivalent work where applicable, finite repeated measurements,
strictly faster TY runtime, and strictly lower complete-process-tree peak RSS.
Expected-violation rows remain correctness evidence until an equivalent-work
performance rule is declared. Policy-comparable rows must satisfy the explicit
`runtime_to_error` or `timeout_dominance` rules, but neither rule converts a
missing both-axis measurement into a strict win.

The broader execution model was described in the supremacy-execution-model
design doc, which has since been removed from the repo (the `designs/` tree
was deleted in commit 2f396435; recover it from git history if needed).
Anti-overfit policy for
engine selection must be structural: benchmark names, module/config names,
paths, expected counts, or corpus membership may appear in policy files and
reports, but not in lowering, selector eligibility, analytical matching, or
cost-model decisions. Analytical solving is a verified engine lane with an
independently checked certificate; it is not a benchmark shortcut and does not
replace TLC/TY parity or matrix evidence for performance claims.

Corpus domination should proceed as a general engine program, not as a
target-list program:

1. Admit work structurally. Eligibility should be derived from syntax,
   representation, transition shape, canonical value kind, shared storage
   policy, fingerprint policy, and verified lowering capabilities, never from
   exact spec names or the current corpus membership.
2. Keep executable gates in Rust. Shell wrappers may select a target directory
   or pass through flags, but `ty supremacy`, `ty canary-gate`, and future
   Rust gate subcommands own selection, policy, telemetry parsing, and failure
   decisions.
3. Treat analytical solving as proof/replay gated. An analytical result can
   help dominate a class only after structural recognition emits a certificate
   and an independent checker or replay path validates the claim against the
   same semantics the matrix uses.
4. Refresh evidence after each engine expansion. A local proof, canary, or
   smoke pass is not enough; the all-runnable matrix must be regenerated from a
   fresh release binary and checked through the Rust matrix/gate path before the
   corpus claim changes.

and adoption rows:

- `origin_frontend` names the source family that produced the row.
- `shared_engine_component` names reusable engine code, not a frontend wrapper.
- `first_beneficiary` and `second_beneficiary` must be concrete and
  non-identical.
- `compatible_frontend_families` must include every concrete family that can
  consume the same canonical contract: `tla_plus`, `quint`, `mcc_petri`,
  `aiger`, `btor2`, `vmt_transition_system`, `ay_analytical`, and
  `witness_replay`. Reserved `future_importer` appears here only when the

- `default_compatible_frontend_families` must list compatible families that
  consume the shared path now.
- `frontend_family_blockers` or an equivalent blocker field must name reserved
  and non-admitted families, especially `future_importer`, instead of omitting
  them from the plan.
- `canonical_fingerprint_identity`, `fingerprint_policy_identity`, and


Use `--mode enforce` only when the full matrix is expected to pass. Without a
matrix policy opt-in, enforcement fails if any row is unsupported, TLC
errors/timeouts, TY times out, parity fails, lacks runtime evidence, ties, or
is slower than TLC.

`missing_runtime` means finite positive timing evidence is absent for a row that
otherwise needs runtime samples before it can become non-blocking. Some terminal
outcomes, such as raw TLC timeouts/errors without comparable evidence, TY
timeout, or parity failure, may classify before `missing_runtime`; metadata
backed expected violations and BMC-only checker-error rows are classified before
runtime evidence when the observed terminal outcome matches the expected one.
For otherwise eligible rows, both TLC and TY must have
`runtime_seconds` present, finite, and greater than zero; a null, absent, zero,
or non-positive runtime on either side keeps that otherwise eligible row in
`missing_runtime`. It is not a claim that the spec cannot run, and it is not
counted as a launch win. The Rust matrix report emits
`missing_runtime_diagnostics` with the precise specs that need measurement and a
Rust CLI refresh command.

For machine-readable classification, use `--format json`. The matrix summary
uses schema `ty.supremacy.matrix_summary.v1` and emits top-level `verdict`,
`strict_pass`, `strict_blockers`, `counts`, `next_action_counts`, `rows`, and,
when opted in, `policy`.
Row `class` values are
stable snake-case buckets: `pass`, `expected_violation_match`,
`runtime_to_error`, `timeout_dominance`, `perf_loser`, `missing_runtime`,
`unsupported`, `tlc_error`, `tlc_timeout`, `ty_timeout`, `parity_fail`, and
`perf_tie`. Non-pass rows also carry a Rust-side `next_action` classification,
including `refresh_runtime`, `fix_parity`, `remeasure_perf_tie`, and
`fix_perf_regression`, so the current failure state can be triaged from the
matrix artifact without Python/JQ gates. By default, enforce mode fails when
`strict_blockers` is nonzero.
With a matrix policy opt-in, summaries still report strict blockers, but the
policy verdict uses `policy.blockers` after counting explicitly allowed
comparable outcomes.

By default, `tlc_error` and `tlc_timeout` are still strict blockers. Matching
expected violations become `expected_violation_match` when both sides report the
expected terminal outcome, even when runtime evidence is absent; this prevents
known-invalid specs from being reported as performance work. Metadata-marked
BMC-only rows can also become `expected_violation_match` when normal TLC checking
fails in the expected way. Unverified or mismatched violation rows stay
`parity_fail`, and generic TLC runtime/tool failures stay `tlc_error`. A policy
file may explicitly opt in to other comparable non-strict outcomes for supported
check-mode rows:

```json
{
  "matrix_policy": {
    "allow_runtime_to_error": true,
    "allow_timeout_dominance": true
  }
}
```

Run with `--policy <policy.json>` to enable those opt-ins. `runtime_to_error`
requires a verified matching non-timeout TLC/TY error, finite positive runtimes
on both sides, and a faster TY runtime-to-error. `timeout_dominance` requires
a pre-existing `verified_match=true`, a TLC timeout with finite positive timeout
runtime, a TY pass with finite positive runtime, and no TY error. Timeout-row
refreshes keep the existing `verified_match` value. These classes can satisfy
the policy verdict, but they remain in `strict_blockers`; `unsupported` rows are
never promoted by matrix policy. `missing_runtime` rows are also never promoted
by matrix policy; they remain `missing_runtime` until an atomic refresh obtains
promotable finite positive TLC and TY runtimes. After promotion, the row is
reclassified and may still block on parity or performance. `parity_fail`,
`perf_tie`, and `perf_loser` rows are likewise real blockers, not
policy-comparable outcomes.

All-runnable matrix closure strategy:

1. Treat `unsupported` as a source-mode or TLC not-runnable blocker. Treat raw
   `tlc_error` and `tlc_timeout` as blockers unless the row reclassifies as
   `expected_violation_match`, `runtime_to_error`, or `timeout_dominance` under
   its evidence and matrix policy; TY unsupported/error outcomes for
   TLC-runnable rows are `parity_fail`, not `unsupported`.
2. Convert `missing_runtime` rows with the Rust matrix runtime collector. The
   default refresh scope selects rows classified as `missing_runtime`; the
   `all-runnable` scope plans every non-`unsupported` row, batches the batchable
   rows, and reports non-batchable blocked rows in `runtime_batch_plan.json`.
   Check-mode rows run one TLC sample and one TY trust-cg sample.
   Simulation/generate rows run TLC in simulation/generate mode and TY through
   `ty simulate`, with simulation completion/parity semantics rather than
   trust-cg check-mode state-count parity.
3. Convert `perf_loser` rows with targeted performance work only. The current
   loser set is `dijkstra-mutex_Safety-4-processors`; it needs backend/runtime
   fixes before the matrix can pass in enforce mode. `MCReachabilityTestAllGraphs`
   is no longer a current baseline perf loser after the #4391 targeted refresh.
   For Dijkstra-style mutex specs, the allowed remediation lane is structural:
   finite model-value-keyed function reads/updates, finite model-value set
   difference/enumeration, and quantified mutual-exclusion invariants must either
   become fully admitted by the flat/native-fused path with exact TLC state-count
   parity, or be handled by a proof/replay-gated analytical or partial-order lane.
   Do not solve this class by spec-name selectors, matrix policy exceptions, or
   `perf_loser` promotion; slower or count-mismatched rows remain blockers.

Runtime refresh prerequisites and defaults:

- Run from the repository root. For final enforce collection, omit
  `--ty-bin` so the Rust CLI owns executable selection and build identity
  checks. For matrix runtime refresh, build the release CLI binary immediately
  before collection and either omit `--runtime-ty-bin` so the collector uses
  the current executable, or pass that freshly built release binary explicitly.
  Passing an old executable is only checked for executability and trust-cg
  availability; it is not proof that the binary matches current source.
- The baseline must provide check-mode source paths. `source.tla_path` and
  `source.cfg_path` resolve under `inputs.examples_dir`; when that field is
  absent, the collector defaults to `~/tlaplus-examples/specifications`.
  Runtime-refresh planning treats config-free rows structurally from source
  metadata or source text, not from an exact spec-name allowlist; those rows use
  a generated TLC config plus TY `--no-config --init MyInit --next MyNext
  --inv TypeOK` flags. The Rust collector writes a refresh plan before runtime
  collection, reports `batchable_runtime_specs`, `blocked_runtime_specs`, and
  ready-to-pass `batchable_runtime_spec_args`, then selects only batchable
  `missing_runtime` rows for default batch execution.
- The TLC jar must exist. `--runtime-tlc-jar` defaults to `TYTOOLS_JAR`,
  then `TLC_JAR`, then `~/tlaplus/tytools.jar`.
- Before collecting any matrix runtime row,
  `ty supremacy matrix --refresh-runtime` preflights the selected
  `--runtime-ty-bin` with a tiny `ty check --backend trust_cg` run using the
  matrix runtime env. The runner clears ambient `TY_*` variables, applies
  the matrix refresh env, and assigns each spec its own `TY_CACHE_DIR`. This
  env enables trust-cg/compiled-BFS diagnostics but intentionally omits
  `full-native-fused` launch-corpus strict variables such as
  `TY_TRUST_CG_NATIVE_CALLOUT_SELFTEST=strict` and
  `TY_TRUST_CG_NATIVE_FUSED_STRICT=1`; ordinary corpus rows that cannot use
  native fused loops must still be measurable. If the binary reports
  `backend_unavailable`, times out, or exits nonzero, the Rust collector
  refuses the batch instead of writing partial runtime evidence.
- `--runtime-ty-bin` defaults to the current executable. Prefer omitting it
  under `cargo run`; pass an explicit release binary only when that binary was
  built immediately before the refresh.
- Debug-profile TY binaries are rejected when collecting any real row.
  Runtime output that includes debug-build or profiling markers is also treated
  as non-promotable unless `--allow-debug-runtime` is set. That override exists
  only for local smoke evidence and is rejected by `--mode enforce`.
- Refreshed baselines that carry `matrix_runtime_refresh_metadata_warning` or
  `ty_refresh.allow_debug_runtime=true` are not valid enforce-mode evidence.
- `--runtime-timeout` defaults to 300 seconds per TLC or TY subprocess and
  must be at least 1.
- `--runtime-output-dir` defaults to
  `reports/perf/<UTC>-supremacy-matrix-runtime`.
- `--runtime-scope` defaults to `missing-runtime`, which refreshes rows that
  lack TLC or TY runtime evidence. Use `--runtime-scope all-runnable` or
  `ty supremacy matrix-full-suite` for the full batchable all-runnable
  refresh path.
- `--runtime-limit` is optional. Omit it, and omit `--runtime-spec`, to run the
  one-command full selected batchable suite. Set it only to chunk long
  refreshes without constructing Python/JQ spec allowlists. The limit is a hard
  cap on total sampled specs for the invocation: simulation rows consume slots,
  regular rows consume slots, and any remaining planned rows are recorded as
  skipped by the limit in `runtime_batch_plan.json`.
- `--runtime-community-modules` defaults to `COMMUNITY_MODULES`, then
  `~/tlaplus/CommunityModules.jar` when present. `--runtime-tla-library`
  defaults to `TLA_LIBRARY`, then `TLA_PLUS_LIBRARY`, then
  `~/tlapm/library` when present.
- `ty supremacy benchmark --specs <name>` has built-in catalog entries for
  the final corpus. Other spec names fall back to
  `tests/tlc_comparison/spec_baseline.json` and are accepted only when the
  baseline row has check-mode source paths. This fallback is for diagnostics
  and matrix expansion; it does not change the final `full_native_fused`
  launch corpus.

Runtime refresh artifacts:

- `$OUT/runtime_batch_plan.json` uses schema
  `ty.supremacy.matrix_runtime_batch_plan.v1`. It records the full Rust
  selected runtime refresh plan, selected runtime specs, specs skipped by
  `--runtime-limit`, and blocked specs with readiness reasons. This replaces
  Python/JQ wrapper lists for "run everything that can run, report what cannot."
- Each normal check-mode sampled spec gets `$OUT/<spec>/tlc-run1/` and
  `$OUT/<spec>/ty-trust_cg-run1/` directories with `command.json`,
  `stdout.txt`, and `stderr.txt`. Simulation/generate and no-config rows use
  mode-specific run directories. If collection setup fails before a command can
  run, the row is recorded under `$OUT/<spec>/collection-failed/<mode>/`.
  `command.json` uses schema `ty.supremacy.command.v1` and records argv, cwd,
  return code, elapsed seconds, environment overrides, and timeout status.
- `$OUT/runtime_evidence.json` uses schema
  `ty.supremacy.matrix_runtime_evidence.v1`. It records the source baseline,
  output directory, timeout, optional limit, refreshed baseline path, refreshed
  matrix path, runtime batch plan path, selected specs, blocked specs, runtime
  provenance metadata, and one row per sampled spec. The
  metadata includes the evidence timestamp, TY git commit, TY binary
  path/SHA-256, TLC jar path/SHA-256, `java -version` output, and the examples
  checkout commit/dirty state. Each row includes `spec`, `tlc`, `ty`,
  `verified_match`, and `refreshed`; each mode includes `status`,
  `runtime_seconds`, `states`, `error_type`, and `artifact_dir`. Collection
  failures are also summarized in the top-level `errors` array with
  `error_type=runtime_collection_failed`; enforce mode rejects any selected row
  that did not produce promotable fresh evidence.
- Matrix runtime evidence is durable only as an immutable artifact set: keep
  `runtime_evidence.json`, `runtime_batch_plan.json`,
  `spec_baseline.refreshed.json`, `matrix_after_refresh.json`, and every sampled
  per-run `command.json`/`stdout.txt`/`stderr.txt` directory together. A copied
  `matrix_after_refresh.json` without its runtime evidence and command artifacts
  is a summary, not durable evidence. The next chunk resumes from
  `spec_baseline.refreshed.json`; the previous output directory remains
  evidence, not a mutable checkpoint.
- `$OUT/spec_baseline.refreshed.json` is a durable baseline copy. It updates a
  sampled row only when both TLC and TY have finite positive runtime evidence
  that is not invalidated by `backend_unavailable`, debug-build, or profiling
  markers. Non-timeout rows also update `verified_match` from refreshed
  pass/parity or matching expected-violation evidence; timeout rows keep the
  existing `verified_match` value. Rows without promotable runtime evidence
  remain unchanged in warn mode and fail the command in enforce mode. For
  refreshed rows, TY `last_run` and `git_commit` are replaced with the current
  runtime-refresh timestamp and TY commit so fresh timings do not retain stale
  diagnose-run provenance. Supported schema-v3 baselines also get a refreshed
  top-level `ty_refresh` block with the runtime-refresh command, updated spec
  counts, timestamp, git commit, and TY binary path/SHA-256.
- `$OUT/matrix_after_refresh.json` is the matrix summary produced by
  classifying `spec_baseline.refreshed.json`.

Useful triage loop:

```bash
# Classify the current baseline.
"$TY" supremacy matrix \
  --baseline tests/tlc_comparison/spec_baseline.json \
  --mode warn \
  --format markdown

# Collect runtime evidence for every batchable all-runnable row without Python
# gates, shell wrapper scripts, or hand-built allowlists. Omitting
# --runtime-limit is the full-suite runtime-evidence path. The command still
# classifies the whole baseline; non-batchable rows remain reported.
OUT=reports/perf/supremacy-matrix-runtime-full
"$TY" supremacy matrix-full-suite \
  --baseline tests/tlc_comparison/spec_baseline.json \
  --mode warn \
  --format human \
  --runtime-output-dir "$OUT"
```

For chunked closure, prefer `--runtime-limit <N>` over hand-built
`--runtime-spec` lists. Each invocation plans rows from the selected
`--runtime-scope`, runs selected batchable planned rows, reports blocked rows in
`runtime_batch_plan.json`, writes a refreshed baseline copy, and leaves rows
unchanged unless both subprocesses produce promotable finite positive runtime
evidence. For explicit `--runtime-spec` lists, `--runtime-limit` still hard-caps
the selected rows and reports the truncated batchable specs in
`skipped_batchable_runtime_specs_by_limit`. Resume by feeding the previous invocation's
`spec_baseline.refreshed.json` into the next Rust CLI invocation; the output
directory itself is not a checkpoint. Repeat until `matrix_after_refresh.json`
reports no stale runtime/perf blockers or the batch plan reports only blocked
rows. Use `--runtime-spec` only for targeted stale rows.

```bash
# Resume/chunk example after a full or partial refresh.
NEXT=reports/perf/supremacy-matrix-runtime-resume
"$TY" supremacy matrix \
  --baseline "$OUT/spec_baseline.refreshed.json" \
  --mode warn \
  --format human \
  --refresh-runtime \
  --runtime-scope all-runnable \
  --runtime-output-dir "$NEXT" \
  --runtime-limit 25
```

With `--refresh-runtime`, stdout prints the same post-refresh matrix summary
used for enforcement. The refreshed classification is also written to
`$OUT/matrix_after_refresh.json`; re-run the matrix command with
`--baseline "$OUT/spec_baseline.refreshed.json"` only when you want to classify
the refreshed baseline in a separate invocation.

```bash
# Only after missing-runtime and perf blockers are cleared, try enforcing the
# all-runnable claim through the Rust matrix.
"$TY" supremacy matrix \
  --baseline "$OUT/spec_baseline.refreshed.json" \

```

Smoke gate for the final target specs:

```bash
OUT=reports/$(date -u +%Y%m%dT%H%M%SZ)-trust_cg-single-thread-smoke
"$TY" supremacy smoke \
  --output-dir "$OUT" \
  --specs EWD998Small MCLamportMutex CoffeeCan1000BeansSafety \
  --timeout 300
```

Strict smoke evidence requires native selftest markers for every final target
spec. CoffeeCan1000BeansSafety must report `4/0/1`, EWD998Small `15/1/3`, and
MCLamportMutex `27/1/3` prepared/action/state-constraint-or-invariant marker
counts with `missing_expected=0`, `fail_closed=true`, and the complete marker
present. The EWD action total is the executable native-fused specialization
count after inner `EXISTS` expansion. Bounded smoke, including Coffee/EWD
strict bounded smoke, is prerequisite readiness evidence only. It is not launch
evidence unless followed by the final `full_native_fused` supremacy gate with
exact TLC/interpreter/trust-cg parity and both wall-clock and compiled-BFS
execution speedups.

Transitional interim action-only native-fused diagnostic, before requiring
trust-cg-compiled invariants:

```bash
OUT=reports/$(date -u +%Y%m%dT%H%M%SZ)-trust_cg-single-thread-action-only-native
"$TY" supremacy gate \
  --mode warn \
  --gate-mode interim-action-only-native-fused \
  --output-dir "$OUT" \
  --runs 3
```

This interim mode is only for the action-only native fused trust-cg parent loop:
actions and the native fused level must be active, flat/global dedup remains in
the normal BFS path, and invariant diagnostics may fall back only to Rust
checking after that dedup. It intentionally does not require all trust-cg
invariants to compile; that requirement belongs to the strict
`full_native_fused` gate. Action lowering fallbacks, missing native actions,
non-native fused levels, or missing flat-frontier evidence still fail the gate.

Final benchmark collection and policy verdict must run through the Rust CLI. The
Rust gate reads `tests/tlc_comparison/single_thread_supremacy_gate.json`,
injects the required interpreter/trust-cg environment for the selected gate mode,
uses the final corpus, runs at least three TLC/interpreter/trust-cg samples, writes
the benchmark summary, and then evaluates that summary with the Rust verdict
engine:

```bash
OUT=reports/$(date -u +%Y%m%dT%H%M%SZ)-trust_cg-single-thread-supremacy
"$TY" supremacy gate \
  --mode enforce \
  --gate-mode full-native-fused \
  --output-dir "$OUT" \
  --runs 3
```

To inspect an existing benchmark or matrix-summary artifact without rerunning
TLC/TY subprocesses, run the Rust verdict engine over the produced summary.
For matrix summaries, the verdict requires current build identity, matching
binary hash, non-debug runtime evidence, a recorded runtime timestamp, matching
baseline corpus digest and row spec set, internally consistent strict counts,
`verdict=pass`, zero counts-derived policy blockers under the loaded supremacy
policy's `matrix_policy`, every row classified as `pass`,
`expected_violation_match`, or a policy-accepted
`runtime_to_error`/`timeout_dominance` comparable outcome, and row classes that
match the recomputed baseline policy classes. Accepted class names alone are not
sufficient. Without those opt-ins, the verdict still requires `strict_pass=true`
and `strict_blockers=0`. A matrix summary cannot replace the final three-spec
single-thread launch command, even when every row is non-blocking; it supports
the broader all-runnable claim only.
This artifact recheck is diagnostic only; do not cite it as fresh launch
collection. Final launch acceptance still requires running the fresh collection
gate above without `--summary-json`. To recheck an existing summary, use:

```bash
"$TY" supremacy gate \
  --mode enforce \
  --gate-mode full-native-fused \
  --runs 3 \
  --summary-json "$OUT/summary.json"
```

With `--runs 3`, the `require_trust_cg_faster_than_tlc` policy requirement checks
that the trust-cg median runtime beats the TLC median runtime for every listed
target spec. It does not claim every individual wall-clock sample beats TLC.
Launch evidence also requires the `require_trust_cg_execution_faster_than_tlc`
policy requirement, which recomputes speedup from positive
`compiled_bfs_execution_nanos` telemetry; wall-clock speedup alone is not
sufficient.

The Rust gate reads the policy file and defaults to `full-native-fused` in
`--mode enforce`. For non-enforce/dev runs, pass an explicit `--gate-mode` so
the artifact records the intended policy mode; use
`interim-action-only-native-fused` only for action-only native-fused
diagnostics. Strict `full_native_fused` policy evidence requires all trust-cg
invariants compiled plus
`trust_cg_native_fused_regular_invariants_checked=true` and
`trust_cg_native_fused_invariant_count=trust_cg_invariants_total`, native selftest
evidence for every final target spec, and `speedup_trust_cg_vs_tlc > 1.0` for
CoffeeCan1000BeansSafety, EWD998Small, and MCLamportMutex using full
wall-clock medians. The `full-native-fused` launch-corpus gate also recomputes
`speedup_trust_cg_execution_vs_tlc` from positive per-run
`compiled_bfs_execution_nanos` telemetry and requires that execution-only
speedup to be greater than `1.0`; this prevents launch evidence where trust-cg
wins only through accounting artifacts while the compiled single-thread loop is
slower than TLC. The protected `full_native_fused` env pins
`TY_TRUST_CG_NATIVE_CALLOUT_COMPILE_JOBS=1`, enables native local dedup with
`TY_TRUST_CG_NATIVE_FUSED_ENABLE_LOCAL_DEDUP=1`, and disables artifact-cache
reuse so recorded wall-clock evidence uses the policy-required native fused
configuration. The stable native fused telemetry
contract is a coarse
`trust_cg_bfs_level_loop_kind=native_fused_trust_cg_parent_loop` plus
`trust_cg_native_fused_mode=action_only|invariant_checking|state_constraint_checking`;
do not encode the mode in the loop-kind string. In the final single-thread
supremacy gate, CoffeeCan1000BeansSafety must report `invariant_checking` with
`trust_cg_native_fused_state_constraint_count=0`, while EWD998Small and
MCLamportMutex must report `state_constraint_checking` with
`trust_cg_native_fused_state_constraint_count=1` and `1/1 state constraints
compiled`. Native fused evidence must also show the compiled BFS level loop
was built, actually started, and completed useful work:
`trust_cg_native_fused_level_built=true`,
`compiled_bfs_level_loop_started=true`,
`compiled_bfs_level_loop_fused=true`, positive
`compiled_bfs_level_loop_initial_states`, and positive
`compiled_bfs_levels_completed`, `compiled_bfs_parents_processed`,
`compiled_bfs_successors_generated`, `compiled_bfs_successors_new`, and
positive `compiled_bfs_execution_nanos`.
The `full-native-fused` launch-corpus gate also requires
`compiled_bfs_total_states == states_found` for each trust-cg run, so a run cannot
pass on native loop activation telemetry unless the compiled loop's final state
count matches the benchmark result.

CoffeeCan1000BeansSafety is a benchmark-local generated wrapper around the
upstream CoffeeCan module with `MaxBeanCount <- 1000`, `INIT SafetyInit`,
`NEXT Next`, and only the `TypeInvariant` invariant. It is the only CoffeeCan
entry used for final TLC timing because the upstream CoffeeCan1000Beans config
contains temporal/liveness obligations that are not part of the TY safety
hot-path comparison. Strict native-fused smoke and final TLC supremacy evidence

and MCLamportMutex. Separate diagnostic runs may still name upstream
CoffeeCan1000Beans explicitly with `TY_SKIP_LIVENESS=1`, but those runs are
not strict smoke or final TLC supremacy evidence.
The final benchmark harness also pins expected state counts for the final
corpus: CoffeeCan1000BeansSafety `501500`, EWD998Small `1520618`, and
MCLamportMutex `724274`. TLC/TY parity at any other state count fails.

### Artifact Freshness Invariant (Opt-In)

For baseline/benchmark tracking issues that must block stale artifacts from driving planning:

1. Add issue label: `artifact-freshness`
2. Add this marker and metadata block to the issue body:

````markdown
<!-- ARTIFACT_FRESHNESS_REQUIRED -->
```json
{
  "canonical": {
    "git_commit": "abc1234",
    "run_date": "2026-02-09T07:10:00Z",
    "test_count": 120
  },
  "diagnostic": {
    "git_commit": "abc1234",
    "run_date": "2026-02-09T07:12:00Z",
    "test_count": 120
  }
}
```
````

When `artifact-freshness` is present, `gh issue edit ... --add-label do-audit|needs-review`
is blocked unless metadata passes validation:
- `canonical` and `diagnostic` sections both present
- `git_commit`, `run_date`, and `test_count` present in both
- `canonical.git_commit` must be a clean 7-40 hex commit
- `run_date` must be valid ISO-8601 and within freshness window (default 14 days)
- `test_count` must be a positive integer

This preserves diagnostic artifacts for debugging while requiring a clean canonical
artifact before workflow phase transitions.
